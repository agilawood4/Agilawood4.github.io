Tokenizer 与 Chat Template

通过本章，我们介绍自然语言怎样真正变成 LLM 可处理的 Tensor，以及聊天数据怎样变成模型实际看到的 Token 序列

其主要经历如下几个阶段：

Tokenizer

LLM 不能直接处理字符串，模型真正接收的是整数（Token ID）序列，所以需要分词器（Tokenizer）

它完成两件最重要的事：分词和词表映射，其中分词表示把一段连续的自然语言文本拆分成若干个词元，也就是所谓的 Token，而词表映射则把每个 Token 映射为对应的整数 Token ID

Vocabulary

Vocabulary 即词表，可以理解为一个映射器，负责建立 Token 和 Integer ID 之间的一一映射

例如：

如果 Vocabulary Szie 为 VVV，那么合法的 Token ID 大致位于：

0∼V−10\sim V-1 0∼V−1

这和上一章我们介绍的下游 LM Head 的输出形状：

logits: [B,L,V]\text{logits: }[B,L,V] logits: [B,L,V]

完全对应，因为模型每个位置实际上都在对 Vocabulary 中的所有 Token 打分

Subword Tokenization

现代 LLM 一般不会把一个汉字或者一个 English Word 映射为一个 Token ID，而是通常采用子词分词（Subword Tokenization）

比如一个比较长的单词 unbelievable，可能被拆成 un，neliev，able 然后分别映射到三个 Token ID；又比如中文里的词组 “卫星导航”，可能被拆分为 “卫星”，“导航” 然后分别映射到两个 Token ID

具体拆分方法完全由 Tokenizer 的词表和分词规则所决定

之所以使用 Subword 的方式，主要是为了复用已有词的映射，比如如果我们已经有了 GNSS，Based 的表示，那么就可以对 GNSS Based 拆分后复用已有的表示

所以对于 Tokenizer 的预训练目标就是使得 Vocabulary 不至于无限大，又能够表达任意文本

现在我们对 Token 有更加清晰的认识：Token 不是自然语言中的词，而是 Tokenizer 根据自己的 Vocabulary 定义出的基本离散单位

Attention Mask

有 Padding 以后会产生一个问题，模型无法区分 Padding 和真正的 Token，如果不告诉模型哪些是我们 Padding 掉的无效位置，它会把这些位置也拿来计算 Attention

三种 Mask 区分

Causal Mask：Transformer 推理的时候不允许看到未来的 Token，也就是未来 Token 信息不参与 Attention 计算

Attention Mask：Padding Token 信息不参与 Attention 计算

Loss Mask：被 Loss Mask 掩码的 Token 不参与 Loss 计算
